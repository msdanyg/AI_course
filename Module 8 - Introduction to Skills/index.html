Skills 101: What They Are and Why They Matter

Every conversation you start with Claude begins from zero. You re-explain your role. You re-state how you want output formatted. You re-paste the same context document for the third time this week. Multiply that across a year and you are paying a tax measured in hours: the repetition tax.

Projects fix part of this problem. They give Claude a persistent workspace inside one mission. But Projects have a ceiling — they are bound to one workspace. The methodology you build inside your Competitive Intelligence project does not travel with you when you open a fresh chat to draft a customer email. Each project is an island.

A Skill is the bridge between islands. If a Project is a mission archive, a Skill is a Mission Card: a standardized procedure, written once, that any pilot in your squadron can pull from the playbook and run on any mission, in any conversation, in any project.

The Defining Characteristic

Claude reads the description and decides on its own whether to fire the skill. You do not need to remember the skill exists. You do not need to type a special command. The trigger is your natural language, and the description is the gate. This makes the description the most important line in the entire skill.

Skills versus Projects

Project Skill
Stores documents, history, custom instructions Stores methodology, steps, output templates, gotchas
Bound to one workspace Available in EVERY conversation, EVERY project
You enter the project to use it Auto-fires when your message matches the description
Persistent CONTEXT Portable METHODOLOGY

# Extracting Gmail Action Items

## Steps
1. Determine the time range (default: last 7 days)
2. Search Gmail using the connector
3. Filter for messages from internal teammates and ActivTrak senders
4. Extract action items, deadlines, and priority signals
5. Return a structured to-do list

## Output format
| Sender | Subject | Action | Due | Priority |

## Gotchas
- Marketing emails contain false action verbs; ignore them
- Calendar invites are not action items
- Automated notifications are usually not actionable

The 5 Skill Killers

When skills fail, they fail in five recognizable ways. Memorize this list. It is the most useful diagnostic in the entire module — the next time a skill misbehaves, this list tells you which knob to turn.

⚠️ Killer 1: Vague Descriptions

Symptom: the skill never auto-fires. You always end up invoking it manually.

Why it happens: the description is written as a summary instead of a trigger.

Fix: write the description in specific, loud, third person. List the actual phrases the user says. "Use when the user asks to summarize their inbox, find action items in recent emails..."

⚠️ Killer 2: Over-Defined Processes

Symptom: the skill works on simple cases but produces stilted, robotic output on edge cases.

Why it happens: too many steps, too tightly specified.

Fix: match degrees of freedom to the task type. Tight for fragile operations (filing a Jira ticket with the right project, label, assignee). Loose for creative work (drafting an email).

⚠️ Killer 3: Stating the Obvious

Symptom: the skill is bloated; behavior does not match the file length.

Why it happens: the author wrote down everything Claude already does well.

Fix: challenge every paragraph. Cut anything Claude does natively. The skill should contain only what is unique to YOUR way of working.

⚠️ Killer 4: Missing Gotcha Section

Symptom: works on the cases the author tested, fails consistently on edge cases anyone would have anticipated.

Why it happens: the author shipped the skill without writing down what could go wrong.

Fix: every skill needs a gotcha section listing failure patterns you have actually seen. This is the highest-signal content in the entire skill.

⚠️ Killer 5: Monolithic Structure

Symptom: the SKILL.md is 1,500 lines long, and Claude starts skipping sections.

Why it happens: the author kept adding to the same file instead of splitting it.

Fix: hard cap at 500 lines. Move detail into companion files. The main file should be a map; the reference files are the territory.

The Litmus Test

🎯
If you find yourself iterating on the output AFTER the skill runs, the skill itself needs improvement. The fix is not to write a better follow-up prompt. The fix is to upgrade the skill. Move the cleanup logic into the skill itself. The whole point of a skill is that you do NOT have to remember to ask for the cleanup. Encode it once, get it forever.

Debugging Decision Tree

Symptom Killer Fix
Skill never auto-fires 1. Vague description Add user phrases to the description
Robotic on edge cases 2. Over-defined Loosen steps; match freedom to task
Bloated, generic output 3. Stating the obvious Cut what Claude does natively
Predictable failure modes 4. Missing gotcha Document failure patterns
Claude skipping sections 5. Monolithic 500-line cap; companion files

Building Your Playbook

You do not have to build every skill from scratch. Anthropic maintains an official skill catalog, and the broader plugin ecosystem includes thousands more. Before building, look. Then build only what does not already exist.

Your First Install: Skill Builder

The first skill you should install is Skill Builder itself. The official name is skill-creator. It is the skill that helps you build skills.

Once installed, you can build new skills inside any Claude conversation by saying something like "I want to build a skill that helps me prep for QBRs." Claude will recognize the request, fire skill-creator, and walk you through the design conversation.

✓ The Skill Builder Conversation 
You: I want to build a skill that extracts action items from my Gmail.

Skill Builder:
- What phrases would you say to invoke this skill?
- What inputs should the skill accept (time range, sender filter)?
- What should the output look like?
- What edge cases or failure modes have you seen?

You: [paste your paper design from the lab]

Skill Builder: [drafts a SKILL.md you can refine]
💡
Where Skill Builder helps most: the structure. New authors consistently underweight the description and overweight the steps. Skill Builder catches this by asking, early, "what does the user say to make this fire?"
⚠️
Where Skill Builder needs YOUR help: the gotcha section. Claude has not lived your work. The gotcha section is where YOUR judgment lands. Do not let Skill Builder write it for you.

Best Practices Compressed

  • One job per skill. If you cannot describe the skill's purpose in one sentence, it is probably two skills. Split it.
  • The description is a trigger, not a summary. Write for the model asking "should I fire here?"
  • Show, do not describe, the output. A literal template is worth ten paragraphs.
  • Document gotchas explicitly. Failure patterns are the highest-signal content.
  • Match degrees of freedom to the task. Tight for fragile operations. Loose for creative work.
  • Context binding rule. Assets ABOUT the skill live with the skill. Assets ABOUT you or your organization live outside and get referenced.
  • Keep it under 500 lines. Move depth into companion files.
  • Ship preference skills. Your competitive advantage is your methodology.

Maintenance Cadence

Quarterly review (every 90 days):

  • Re-evaluate capability skills — did a model upgrade obsolete any?
  • Re-read every preference skill — has your workflow shifted?
  • Audit each skill against the 5 Killers
  • Apply the Litmus Test to each skill's recent output

Part 1: Feel the Loop (4 minutes)

Before you build, experience how someone else's skill behaves end-to-end. This grounds everything that follows.

Task 1A: Browse the catalog

Open the Skill catalog inside Claude. Scan ten skills. Read their descriptions, not their names. Notice the patterns:

  • Good descriptions list ACTUAL phrases users say
  • Good descriptions are written in third person ("Use when the user asks to...")
  • Bad descriptions read like marketing copy

Task 1B: Install your first skill

Pick one skill that maps to your real work. Suggested options:

  • skill-creator — the official Skill Builder (you will need this in Part 3)
  • A research skill if you do competitive intelligence
  • A writing skill if you draft a lot of customer-facing content

Task 1C: Trigger it twice

  • Auto-invocation test: type a natural sentence that matches the description. Do NOT mention the skill by name.
  • Manual invocation test: explicitly tell Claude to use the skill by name. Compare.
📝
Reflection: Did the skill auto-fire on your first natural sentence? If not, what did the description NOT match? This is your first encounter with Killer 1 in the wild.

Part 2: Design on Paper (5 minutes)

Stop. Before you open Skill Builder, design your Gmail skill the old-fashioned way. Skills built without a paper design produce vague descriptions and bloated steps.

Worksheet

📋 Your Skill Design 
SKILL NAME (gerund-form, lowercase, hyphenated):
extracting-gmail-action-items

DESCRIPTION (third-person, list 3-5 user phrases):
Use when the user asks to:
- "summarize my inbox"
- "find action items from this week's emails"
- "what do I owe people"
- "pull my to-do list from email"
- "what's outstanding in Gmail"

The skill searches Gmail via the connector, filters for messages
from internal teammates and ActivTrak senders, extracts action items
with deadlines and priorities, returns a structured to-do list.

INPUTS:
- Time range (default: last 7 days)
- Sender filter (default: internal + ActivTrak)
- Label filter (optional)

OUTPUT TEMPLATE (literal, not described):
| Sender | Subject | Action | Due | Priority |

GOTCHAS (failure patterns you can predict):
- Marketing emails contain false action verbs; ignore
- Calendar invites are NOT action items (unless body asks)
- Automated notifications (Jira, Monday) are usually noise
- "FYI" and "no action needed" should be skipped
- Internal forwards: evaluate by ORIGINAL sender's intent

CONSTRAINTS:
- Never include emails older than 30 days
- Never surface personal/private emails
- If fewer than 3 items found, ask to expand time range

Part 3: Build with Skill Builder (10 minutes)

Now you bring the paper design into Claude.

Task 3A: Invoke Skill Builder

In a fresh Claude conversation, type:

✓ Trigger 
I want to build a skill that extracts action items from my Gmail.
It should filter for messages from internal teammates and ActivTrak
senders, extract real action items (not marketing or notifications),
and return a structured to-do list with sender, subject, action,
due date, and priority.

Skill Builder should auto-fire. If it does not, type /skill-creator to invoke manually. Note this — manual invocation when auto should have fired is itself a Killer 1 symptom on Skill Builder's description.

Task 3B: Walk the conversation

Use your paper worksheet to answer Skill Builder's questions fast and consistently. Paste the description phrases, the steps, the literal output template, and your gotchas.

⚠️
Critical: Do NOT let Skill Builder write the gotcha section for you. Skill Builder has not lived your work. The gotcha section is where YOUR judgment lands.

Task 3C: Review the generated SKILL.md

Run this checklist on the draft Skill Builder produces:

  • ☐ Description in third person
  • ☐ Description lists actual user phrases
  • ☐ Steps are numbered (not prose)
  • ☐ Output format is a literal template
  • ☐ Gotcha section is present and specific
  • ☐ File is under 500 lines

Part 4: Test Against Real Gmail (5 minutes)

Now you fly the skill. In a fresh Claude conversation (no project, no special setup), run all three tests as natural sentences:

Test 1 — Auto-trigger test 
What do I owe people from this week?
Test 2 — Specific time range 
Pull my action items from the last 3 days.
Test 3 — Edge case 
What's outstanding in my inbox right now?

For each test, record:

  • Did it auto-fire?
  • Was the output structured correctly?
  • Did it filter out marketing and automated notifications?
  • What were the misses or false positives?

Part 5: Apply the Five Killers (5 minutes)

Failures are not failures. They are diagnostic signals. For each failure you noted in Part 4, identify which Killer applies and apply the fix.

The Diagnostic Table

Symptom Killer Fix
Did not auto-fire on natural sentence 1. Vague description Add the exact phrase to the description's trigger list
Robotic / off-format on edge cases 2. Over-defined process Loosen the relevant step
Output included generic email summary 3. Stating the obvious Cut the step. Claude does that natively
Returned marketing or calendar invites 4. Missing gotcha Add specific failure pattern to gotcha section
Skill bloated, Claude skipping sections 5. Monolithic Split into companion files

The Litmus Test

🎯
Did you, at any point in testing, find yourself manually cleaning up Claude's output AFTER the skill ran? If yes, the skill is not done. The cleanup belongs INSIDE the skill. Make a note of what to add next.

Apply ONE fix. Pick the most impactful failure. Apply the fix to your SKILL.md. Re-run the failed test. Did the fix work?

📋 Study Guide

Core Mental Model

Project = persistent CONTEXT (one workspace).
Skill = portable METHODOLOGY (everywhere).

A Project remembers facts about a domain. A Skill encodes a way of working that travels across every domain. You use them together — the Project holds the briefing material; the Skill defines how you process briefings.

Anatomy of a SKILL.md

Required structure 
---
name: gerund-form-lowercase-hyphenated
description: Use when the user says "[trigger 1]", "[trigger 2]"...
  Returns [what the skill produces].
---
  1. When to use (trigger phrases)
  2. Steps (numbered, not prose)
  3. Output format (literal template)
  4. Gotchas (failure patterns you have seen)
  5. Constraints (skill-specific rules)

Hard cap: 500 lines. Move depth to companion files.

The Description Recipe

Three rules:

  1. Specific — list actual phrases users type
  2. Loud — concrete words, not abstract concepts
  3. Third person — "Use when the user asks to..."

The Investment Rule

Type Behavior over time Invest
Capability uplift DEPRECIATES (model upgrades obsolete it) 20%
Encoded preference APPRECIATES (executes more cleanly over time) 80%
